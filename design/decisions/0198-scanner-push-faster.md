# 0198 — Scanner: Push to admin makes and uploads its files a few at a time; the shop level runs ~2.5x faster

`2026-11-26` · proposed · Figma: no new component; the push line of the `activity bar` reads "3 of 7 files" instead of "image 1 of 3" / "clip 1 of 2".

**Context.** Gio (2026-11-26): pushes from the Scanner take a long time since the shop samples are levelled (0192). Measured on Gio's own Zoom sides (STE-000…004, 44.1 kHz, 2–3 min): `web-level.js` took 1.7–2.7 s per clip with a JIT (6.5 s for a 3-min 96 kHz side; 25–55 s if JavaScriptCore runs without one). A push did everything one after the other: per photo 4 WebP made from 4 reads of the scan and 4 uploads, then per clip read → level → WAV → LAME → upload.
**Decision.**
- **web-level.js, same result, less work.** The two K-weighting biquads run in one pass without storing the weighted signal; each sample is squared once per 100 ms hop (a 400 ms block = sum of its 4 hops); the per-frame peak is found once for all limiter tries; the linear gain of a frame is computed once (not per channel) and skipped where the limiter has let go (< 1e-7 dB); the trial pass is the result when no make-up follows. On STE-000…004: same gain, reduction and output LUFS to 4 decimals, max sample difference 6e-8 (one float ulp), ~2.5x faster, a few hundred MB less memory on long sides. The admin uses the same file and gets the same speed-up.
- **Push in parallel.** Every photo and clip of a push is its own task, 3 at a time: a clip is levelled and encoded while photos upload. A scan is decoded once for its 4 WebP sizes; the 3 smaller sizes upload together. The admin still receives the files in the plan's order. The WAV writer fills one buffer instead of appending sample by sample (exports benefit too).
- **One token refresh.** With uploads at the same time, an expired session token is refreshed by one request every upload waits for (two refreshes with the same refresh token would sign the app out).
- **Not server-side.** Levelling after upload on the server (Gio's suggestion) was weighed: it needs a worker with the audio decoded (GitHub Actions like 0195 or similar), the shop would play an unlevelled sample until it ends, and a second place where gain is applied risks the "no double gain" rule of 0192. With the levelling now off the critical path the in-app push is fast enough; revisit only if measurements on the Mac say otherwise.
**Rule.** A Scanner job that produces several independent files makes and uploads them concurrently (bounded), and keeps the order of what it reports. Shared shop logic (web-level.js) is optimised in the one shared file, never forked into a native copy.
**Where.** `packages/audio/web-level.js`, `apps/scanner/Sources/AppModel.swift` (`send`), `AudioExport.swift` (`image`, `webp(from: CGImage)`, `wavData`), `Backend.swift` (`token`), `WebLevel.swift`.
