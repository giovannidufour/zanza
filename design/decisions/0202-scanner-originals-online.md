# 0202 — Scanner: the whole-record originals go online with the SKU (Push, and a backfill at launch)

`2026-11-27` · proposed · Figma: no new component; the push line of the `activity bar` and the draft row's job line read "… · 2 originals" after a push, and the backfill shows as "Uploading originals · 12 of 76 originals" / "Originals · 76 originals uploaded".

**Context.** Gio (2026-11-27): the Full scans (the whole record, uncropped) should be online with each listing, not shown in the shop, so they can feed record videos and video covers later. Every Scanner scan of a label already writes the whole record to the Originals folder under the same name `<sku>_<role>_<slug>` (0136/0137; on Gio's Mac 76 JPEG of 4252 px, ~3.5 MB each, for 38 SKUs). The backend exists since 0200: `listings.original_keys` (migration 0045, staging), `sign-upload` kind `original` (R2 `originals/`, JPEG/PNG/WebP up to 20 MB), `purge-media` keeps originals still referenced.
**Decision.**
- **What goes up.** The files of the Originals folder itself (not `Free scans`), image roles only (1, 2, 3…), uploaded as they are (the original JPEG/PNG, no resize, no WebP); a TIFF is made a JPEG (0.92) because sign-upload takes no TIFF. One key per file in `original_keys`, never in `photo_keys`.
- **Push.** After the photos and clips are attached, Push sends the originals of the draft's SKU. They are independent of Replace / Keep (the admin shows no originals, there is nothing to replace by hand). A failure here never fails the push: the result says "originals not uploaded", and the next backfill sends them.
- **Backfill at launch.** Once per launch, after the first draft search while signed in, the Scanner looks for originals whose listing exists (any status: draft, published, sold) and that are not online yet; only then it queues one job on the push lane ("Uploading originals · n of m"). Nothing to send = no job, no line. SKUs with no listing stay on the Mac.
- **Ledger, no duplicates.** What is online is remembered next to the files, `.originals-online.json` in the Originals folder (file → listing id, size, modification date, key): it survives an app rename or a new bundle id, and moves with the folder. A file is uploaded again only when it changed (a rescan: its new key takes the place of the old one in `original_keys`, the old one goes to the trash via the 0045 trigger) or when its key is no longer on the listing. Keys added by admin → Take photo are never touched. The ledger is saved after each SKU, so an interrupted backfill goes on from there. Push and backfill run one sync at a time.
- **Writes.** `original_keys` is read and written with the admin session straight on the listing (PostgREST, RLS `listings_admin`), as the Price tab (0196): no new Edge Function, no migration, no redeploy. Writing a published listing marks a shop rebuild (0005, one per minute at most); the shop never reads the column.
**Rule.** Originals that are kept but not shown live in `original_keys` (0200); the Scanner sends a file once and knows it from its ledger, never by guessing from the listing.
**Open.** (1) The role of each original (Label A / B side) is only in the ledger, not in the database: when videos use them, either keys in role order or a small `{role, key}` column (migration) · (2) an admin Save of a listing form opened before a push writes its older `original_keys` back (as for photos): the dropped keys go to the trash and the next launch uploads those files again · (3) `original_keys` of published listings is readable through the public API like the other columns (keys are random, files not linked anywhere); a column grant would hide it (migration, Gio's ok) · (4) the admin still does not show or remove originals (0200 open 3).
**Where.** `apps/scanner/Sources/Originals.swift` (files, ledger, sync), `Backend.swift` (`originals(skus:)`, `setOriginals`), `AppModel.swift` (`send`, `backfillOriginals`), `DraftSession.swift` (`search`), `SamplesViews.swift` (activity line).
