# 0150 — Check your wantlist: Discogs OAuth, matched in the visitor's browser

`2026-11-23` · accepted · Figma: page `Wantlist` (2477:3348), BACKEND → `Settings` (`setting`), `footer link list` and `menu layer` (boolean `wantlist`)

**Context.** Gio (2026-11-23): a visitor should see which records of the shop are on their Discogs wantlist, without downloading or uploading a CSV, also when the wantlist is private, and it must be explicit that the shop never sees nor keeps the wantlist. On/off from the admin. Gio's own wantlist is never public and is not involved.
**Decision.**
- **Discogs OAuth 1.0a** (a username lookup would only work for public wantlists: rejected by Gio). Discogs app "rythem-works" on Gio's developer settings; its key and secret live only in Supabase secrets.
- **The server signs, the browser reads.** Discogs answers no CORS preflight, so the browser cannot send an OAuth header; it can fetch a URL that carries the OAuth parameters with an HMAC-SHA1 signature in the query. Edge Function `discogs-oauth` does only what needs the secret: request token, access token, and signing GET URLs for two paths (`/oauth/identity`, `/users/<name>/wants`). The visitor's browser fetches those URLs from api.discogs.com and compares the wantlist with the cards of `/wantlist/` (`data-release`, `data-master`). The wantlist never reaches our server and is never stored; it lives in memory until the check ends. Tested end to end on 2026-11-23 with Gio's private wantlist (4,433 records, ~45 requests ≈ 45 s).
- **No cookies.** The Discogs permission (access token) is kept in `sessionStorage` (this tab only) until the tab closes or Disconnect is pressed; nothing in localStorage. Access can also be removed on Discogs → Settings → Applications.
- **Page `/wantlist/`** (also the OAuth callback): page title + four `step`s that say what happens to the wantlist + "Connect Discogs"; then "Checking your wantlist… n of N records"; then the Search results page (filters, sort, "Show sold out" on: sold records are shown, Gio) with the heading "N records from your wantlist" + "Disconnect Discogs" and two groups under a `section head` (as "More for sale" on the PDP): **Exact matches** (same Discogs release) and **Other pressings** (same master). Every record of the shop (sale and, when on, trade).
- **Entry points:** "Check your wantlist" in the footer's Shop group and in the mobile menu (Gio). 
- **Switch:** admin → Settings → Wantlist check, `shop_settings.wantlist_enabled` (migration 0033). Off = no page, no link, no Privacy line (`{{#wantlist}}`), and the function answers 404.
- **Privacy:** one line (the browser compares, nothing reaches us, the permission stays in the tab).
- **Components:** `trade step` → **`step`** (code `TradeStep` → `Step`, `.zz-step`), now used by How trading works and Check your wantlist. Figma `trade setting` / `identity setting` / `wantlist setting` → one **`setting`** (text props heading, help; checkbox label as override).
**Rule.** Data a visitor brings from another service is read and matched in their browser; a server function may only hold the secret and sign, never receive the data. Anything shown about it says so in plain words.
**Where.** `supabase/functions/discogs-oauth`, `supabase/migrations/20261123300000_wantlist_switch.sql`, `apps/storefront/pages/plp.js` (WantlistTop), `scripts/site.js` (initWantlist, initFilters), `pages/shell.js` (footer, menu), `content/legal/privacy.md`, `apps/admin/admin.js` (Settings), `site.json` → wantlist.endpoint.
