# 0047 — Genre is the Discogs style; the Discogs genre is the macro genre

`2026-11-10` · accepted (Gio) · Figma: BACKEND → Create, section "genre and tags" (`2126:1404`); COMPONENTS → filters; Attributes tabs

**Context.** The shop had a Genre (the Discogs genre, almost always Reggae, never shown) and a Subgenre (the Discogs style: Roots, Dancehall…), which is the only one that matters to buyers. Calling the useful one "subgenre" was misleading everywhere: admin, filters, links, database.
**Decision.** Rename only, no behaviour change. The Discogs style is the **genre** (`genres`, `release_genres.genre_id`, `releases.genres`; admin field "Genres", Attributes tab "Genres", PLP block "Genre", URL `?genre=`, chip "Genre: Roots"). The Discogs genre is the **macro genre** (`releases.macro_genre`; admin select "Macro genre"), kept for the record and never shown in the shop. Migration 0014 renames `genre` → `macro_genre` first, then `style` → `genres` and `subgenres` → `genres`, in one transaction (same rows, ids and slugs). Old links keep working: `?subgenre=` is rewritten to `?genre=` on the PLP, `#attributes/subgenre` opens the Genres tab, and `admin_save_listing` still reads the old payload keys (`genre`, `subgenres`).
**Rule.** Say "genre" for Roots / Dancehall / Lovers and "macro genre" for Reggae / Jazz. Never introduce "subgenre" or "style" again in UI, code or data; "style" stays only where Discogs' own API is described (`discogs-lookup` returns `genres` and `styles` as Discogs names them).
**Where.** `supabase/migrations/20261110120000_macro_genre_and_genre.sql`; `apps/admin/admin.js`; `apps/storefront/data/products.js`, `pages/plp.js`, `pages/shell.js`, `pages/pdp.js`, `build.js`, `scripts/site.js`; `content/products/*.json` (`release.macro_genre`, `release.genres`). Amends the names in 0028, 0031, 0034, 0041.
